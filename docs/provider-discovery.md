# Project-scoped provider discovery

The pinned Desktop asks for provider and model options at `/projects/<project-id>` before it creates a Chat workspace. A fresh installation may have no running workspaces, so that path starts a disposable discovery Pod for the selected, authorized Project. The initial snapshot can be empty while discovery runs. Completion publishes a `providers_snapshot_update` with the same project cwd; Desktop applies that update only to the selected project's catalog. A refresh request is acknowledged before discovery completes.

The pinned daemon normally returns a compact catalog with an empty legacy `entries` array. Discovery expands `compactSnapshot` using the upstream codec before checking availability or storing the catalog. `npm run test:provider-probe` exercises this wire sequence against a disposable unmodified daemon; it requires the locally built `paseo-workspace:dev` image, or an explicit `UPSTREAM_TEST_IMAGE` override.

The probe uses the Project's current repository and revision, credential profile, and effective workspace image. It checks out the repository into an ephemeral volume because OpenCode can read project-local provider and agent configuration. It runs the unmodified Paseo daemon's availability and catalog APIs without creating an agent or submitting a provider prompt. A `ready` entry means the daemon reported a selectable catalog. It is **not** proof that a credential can complete a prompt. The Codex probe receives only the broker's access-only output and uses the same launcher as a workspace; it cannot read or renew the authority credential. Git fetch material is mounted only into the checkout init container. No Kubernetes API token, gateway-scoped workspace token, Git signing key, or persistent workspace volume is mounted into the daemon.

The Pod and Service are owned by the Project UID, carry a unique run label, and use the workspace transport and NetworkPolicy selectors. The Pod runs as non-root with a read-only root filesystem, bounded resources, a one-GiB ephemeral data volume, a 300-second active deadline, and no service account token. Discovery waits at most 240 seconds. A queued request claims no cluster resources; the probe deadline starts only when it receives a concurrency permit. Cleanup checks object ownership and exact created UIDs; an interrupted run is reclaimed after six minutes, with a run-label and Project-UID check only for the narrow create-to-receipt crash gap. Service and Pod deletion must be observed before a result is published. Gateway replacement does not delete a still-running prior gateway's probe. A connected replacement gateway watches the durable catalog record every five seconds so a result completed by the previous gateway still reaches Desktop.

A verified catalog is stored for 15 minutes with a fingerprint of the Project spec/UID, credential profile spec/UID, effective image, and referenced Secret/ConfigMap UIDs and resource versions. A changed configuration triggers a fresh probe; a previous Pod with the same image does not attest the new configuration. Watched projects audit that fingerprint every 30 seconds, including credential-output replacement. A mutable remote Git ref can move without a Project change; its project-local catalog is rechecked when the 15-minute verification expires or on explicit refresh. Only bounded, whitelisted catalog fields are persisted. Routing IDs are preserved exactly; oversized catalogs fail explicitly. Arbitrary daemon errors, provider HTTP bodies, logs, metadata, and SVG are not persisted or relayed. Failures use fixed categories and retry after 30 seconds while an authorized client watches the project. Missing broker output remains unavailable until its reference exists. Discovery allows two concurrent probes per gateway and bounds its queue to 32.

A cold-start acceptance run must use a fresh Desktop preference state and zero Ready workspaces, select an authorized Project, wait for its verified catalog, and create the first prompted Chat. It must also check a second project with a differing profile or image, configuration change invalidation, an unavailable credential projection and recovery, gateway replacement during discovery, and UID-checked cleanup. Source and unit tests establish the route and protocol behavior; a real daemon and Desktop run remains required before calling that end-to-end flow qualified.

If a refresh fails for an unchanged configuration whose providers were previously verified, the gateway publishes non-selectable error entries for those known providers. An initial failure before any provider identity is known returns a sanitized RPC error on request or refetch and keeps a bounded retry schedule. The pinned Desktop protocol has no catalog-wide error field, so its empty picker cannot show a provider-specific error in that case. The gateway does not invent an installed provider to fill that gap. A gateway terminated during discovery can leave its probe for the documented stale-run recovery window; probe shutdown is not yet tied to the gateway's graceful shutdown deadline.
